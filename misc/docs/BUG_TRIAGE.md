## Deploy model

Process: **creating a git tag = deployed.** To decide if a fix is live:

- Find the fix commit: `git log --oneline -i --grep='#<reportid>'` (commit messages reference `BGA #<id>`).
- Is it in the latest tag: `git merge-base --is-ancestor <commit> <latest-tag> && echo LIVE`.
- List tags containing it: `git tag --contains <commit> --sort=creatordate | head`.

In the latest deployed tag -> **Fixed**. Committed/tagged but that tag not deployed -> **Waiting for deploy**. When unsure whether a tag is deployed, ask.

Internal record of triaged reports (root cause, fix, test) - never put this detail in a public bug comment.


- [x] **Treetreader defect 1/3: unlimited activation (BGA #235064).** FIXED, waiting for deploy. Treetreader I/II (`card_ability_2_5`/`_2_6`) carried no `spendUse:`, so the card token never flipped to used and the ability was reusable any number of times per turn (II heals 1/forest-entry, so unlimited = infinite heal). Fixed in [card_ability_material.csv](../../misc/card_ability_material.csv) rows 5/6 (hno=2): `r` carries a per-branch `spendUse:`, Material.php regenerated. Tests `Campaign_TreetreaderBug235064Test::testTreetreaderCanOnlyBeUsedOncePerTurnBug235064` (I) and `::testTreetreaderIIBranchesAndPassiveBug235064` (II, plus the `on=custom` passive still firing with the use spent). NOTE (design record): the per-branch form is deliberate, NOT the wrapped `spendUse:(A/B)` the triage originally proposed - `Card::createOperationForCardEffect` sets `l_confirm`/`l_skip` on the top-level op only and `withData(merge)` strips `l_*` before delegates, so wrapping buries the `Op_or` and loses both the branch prompt and the `effect_1`/`effect_2` button labels that defect 2/3 depends on. Written up in [EFFECTS_DSL.md](EFFECTS_DSL.md). Side benefit: `Op_spendUse` voids on non-Manual events, so Treetreader II (`on=custom`, previously ungated) no longer raises spurious use-card prompts on unrelated triggers.
- [x] **Treetreader defects 2/3 and 3/3: both choice buttons did the opposite of their label (BGA #235064).** FIXED, waiting for deploy. One root cause, one fix. [Op_or::paramInfo](../../modules/php/Operations/Op_or.php#L79) labels `choice_$i` from `effect_(i+1)` (the `<li>` bullets), and the bullets were listed in REVERSE order of the DSL branches, so "Move into an adjacent forest area" ran the unfiltered move and "Move out of a forest area" ran the forest-only move. Fixed by swapping the DSL branches, not the bullets - the bullet order matches the printed card (FORUM.md:7008), and [DESIGN.md](DESIGN.md) requires `<li>` in OR-branch order. `r` is now `(spendUse:move(forest))/(in(forest):spendUse:move)`. Tests `Campaign_TreetreaderBug235064Test::testMoveIntoForestOffersOnlyForestBug235064` and `::testMoveOutOfForestOffersNonForestBug235064`; the 4 Treetreader tests in `Campaign_AlvaAbilityTest` had their choice indices updated. RESOLVED (the triage entry's open design question): "move out" is an unfiltered move BY DESIGN, no non-forest filter. FORUM.md:5305 has the designer allowing forest -> Grimheim, and Grimheim has no terrain type (FORUM.md:5283), so `move(forest)` could never reach it; the forest-to-forest overlap with the other branch is legal either way. Pinned by an assertion in the move-out test.
- [ ] **Treetreader lets Alva walk OUT of Grimheim (pre-existing, found reviewing the #235064 fix).** NOT a reported bug yet. [FORUM.md:7036](FORUM.md#L7036), designer: "Treetreader may move into Grimheim but not out of it." Branch 1 `in(forest):move` is correctly void inside Grimheim (no terrain type), but branch 0 `move(forest)` is ungated: `hex_10_10` is forest and adjacent to Grimheim, and `getReachableHexes` seeds every Grimheim hex at distance 0 when the hero starts inside, so "Move into an adjacent forest area" walks her out of town. Predates the #235064 fix (the same move was offered under the other label before). FIX needs a negated gate, e.g. `notIn(Grimheim):spendUse:move(forest)` - the DSL has `Op_in` but no negation, so this means a new gate op or a `check(...)` bareword. No test yet. NOTE for Victoria: worth confirming this is really illegal before building a new DSL primitive for it.
- [x] **Multi-kill abilities misattribute XP/gold (BGA #234247 Sweeping Strike; #234242 Nailed Together = duplicate).** FIXED, waiting for deploy. [Game::countMonsterXp](../../modules/php/Game.php#L592) ignored the `$context` monster passed by `Monster::finalizeDamage` whenever an attack was in progress and read the monster on the shared `marker_attack` hex instead. `Op_applyDamage` advances that marker to the next target before the earlier kill is finalized, so each kill scored the wrong monster: the Sweeping Strike cleave under-awarded (the second victim was already gone), while the Nailed Together pierce over-awarded (it scored the surviving brute behind). Fixed by preferring `$context` when it is a monster id, keeping the attack hex as the fallback for the `countMonsterXp` bareword, which `Op_counter` calls with the source CARD id. Tests: `Campaign_MultiKillXpBugTest::testSweepMultiKillAwardsXpForEveryMonster` (victims worth different amounts, so it pins attribution not just the count), `GameTest::testCountMonsterXpPrefersContextOverAttackHex`, and an XP assertion added to `Campaign_BjornSoloTest::testNailedTogetherIIChainWithChoice` for the pierce case. All three fail on the pre-fix code.
- [ ] **`killed(<expr>)` quest predicates score the wrong monster in a multi-kill (found reviewing the #234247 fix).** NOT a reported bug yet, and NOT a regression - the reward half is fixed above, this is the quest-tracker half of the same root cause. [Op_killed](../../modules/php/Operations/Op_killed.php) and the `counter(countMonsterXp)` fallback still resolve the killed monster from `marker_attack`, which [Op_applyDamage](../../modules/php/Operations/Op_applyDamage.php) has already advanced. Repro: Bjorn with Nailed Together II killing two 1-XP goblins with a brute behind them advances the Trollbane tracker by 3 instead of 2. Same exposure for Quiver (`killed('rank>=3')`), Leather Purse, Helmet, and `CardEquip_Shield`. FIX: `queueTrigger` in `Op_applyDamage` passes no data - carry the dying monster id (e.g. `["killed" => $defenderId]`) and have `Op_killed` and `Op_counter` prefer it over the marker. No test yet; `Campaign_BjornQuestTest` around line 589 destructures an `$expectedTracker` it never asserts, which is why this stayed invisible - assert it as part of the fix.

- [x] **Nailed Together II chain re-offers 0-piercing after an exact kill -> softlock (BGA #234580).** FIXED, waiting for deploy. [Op_c_nailed](../../modules/php/Operations/Op_c_nailed.php) re-queues `c_nailed(chain)` whenever `$willKill`, so the chain step is created before its overkill is known and can land void: an exact kill leaves 0 overkill, or the kill was the last monster in the line. The plain `queue()` passes no `l_skip` (unlike the card-driven op, which gets it from `Card::createOperationForCardEffect`), so the void step could not auto-resolve -> "Choose a monster to deal 0 piercing damage to" / "No overkill damage". Fixed by overriding `Op_c_nailed::canSkip()` to return true when `noValidTargets()`, matching the `Op_c_reaper`/`Op_moveMonster` idiom. Tests in `Op_c_nailedChainSoftlockTest` (4, three of which fail pre-fix). NOTE: the `l_skip` fix this entry originally proposed was tried and REVERTED - `Operation::canResolveAutomatically()` returns false when an op has valid targets AND is skippable, so it turned every single-target chain step into an optional prompt and broke `Campaign_BjornSoloTest::testNailedTogetherIIChainWithChoice` (brute took 0 chain damage). Do not re-propose it. Related: `Op_applyDamage`, `Op_dealDamage`, `Op_removeDamage` and `Op_gainMana` all have the INVERSE `canSkip()` shape (`noValidTargets()` -> defer to parent, else false) and carry the same latent softlock if ever queued without `l_skip`; #234859 below is that same shape.


## Tracked bugs - posponeded
- [ ] **Sweeping Strike "1 cleave hit per attack" cap not enforced in code (follow-up from BGA #233927, pre-existing).** NOT a reported bug yet - flagged during the #233927 fix. The [Op_c_sweep](../../modules/php/Operations/Op_c_sweep.php) docblock claims at most 1 cleave hit per attack, but nothing enforces it; it relies on overkill running out. A cleave that leaves LEFTOVER overkill (e.g. target health 1, overkill 2) with a third live monster on the hero's ring could chain a second cleave. No test yet. Consider enforcing the cap explicitly (dedicated marker/flag) rather than depending on overkill arithmetic.
- [ ] **Heal / removeDamage softlocks when there is no damage to remove (BGA #234859 red crystals).** CONFIRMED (green test `Op_removeDamageSoftlockTest::testGain3RemoveDamageWithNoDamageSoftlocks`). Gaining red crystals queues `NremoveDamage`; when nothing on the board has damage, [Op_removeDamage::getPossibleMoves](../../modules/php/Operations/Op_removeDamage.php) marks every candidate `ERR_NOT_APPLICABLE` -> `noValidTargets()` true, but [Op_removeDamage::canSkip](../../modules/php/Operations/Op_removeDamage.php#L240) returns false, so `canResolveAutomatically()` is false and the top-level dispatch drops into PlayerTurn with no clickable target and no Skip = softlock. (Top-level dispatch never consults `isVoid()`, which is why only the direct-reward path locks; nested-in-seq is fine.) FIX: `Op_removeDamage::canSkip()` should return true when `noValidTargets()` (auto-skip empty). Same base op is shared by heal/repairCard/`all`-mode, so the one fix covers those latent cases. Flip the `canSkip`/`canResolveAutomatically` assertions once fixed.

- [ ] **Optional step-by-step move mode (idea from BGA #234817, Victoria).** Heroes without a step incentive (e.g. Embla) use one-shot `Op_move` (click the final destination, hero paths there and the action ends); players expecting hex-by-hex clicking think movement "ended early" (it did not - they clicked a near hex). #234817 (Embla move) and #235051 (Boldur Wrecking Ball option not noticed) are this discovery-gap family, resolved Not-a-bug / Info-needed. Idea: offer an optional step-by-step move mode (game preference or per-move toggle) so movement can be click-by-click for any hero. Not a bug; design decision, not started. `Op_actionMove::hasStepIncentive` currently gates step mode; a preference would OR into it.
