## Deploy model

Process: **creating a git tag = deployed.** To decide if a fix is live:

- Find the fix commit: `git log --oneline -i --grep='#<reportid>'` (commit messages reference `BGA #<id>`).
- Is it in the latest tag: `git merge-base --is-ancestor <commit> <latest-tag> && echo LIVE`.
- List tags containing it: `git tag --contains <commit> --sort=creatordate | head`.

In the latest deployed tag -> **Fixed**. Committed/tagged but that tag not deployed -> **Waiting for deploy**. When unsure whether a tag is deployed, ask.

- [x] **Treetreader defect 1/3: unlimited activation (BGA #235064).** FIXED, waiting for deploy. Treetreader I/II (`card_ability_2_5`/`_2_6`) carried no `spendUse:`, so the card token never flipped to used and the ability was reusable any number of times per turn (II heals 1/forest-entry, so unlimited = infinite heal). Fixed in [card_ability_material.csv](../../misc/card_ability_material.csv) rows 5/6 (hno=2): `r` is now `(in(forest):spendUse:move)/(spendUse:move(forest))`, Material.php regenerated. NOTE (design record): the per-branch form is deliberate, NOT the wrapped `spendUse:(A/B)` the triage originally proposed - `Card::createOperationForCardEffect` sets `l_confirm`/`l_skip` on the top-level op only and `withData(merge)` strips `l_*` before delegates, so wrapping buries the `Op_or` and loses both the branch prompt and the `effect_1`/`effect_2` button labels that defect 2/3 depends on. Written up in [EFFECTS_DSL.md](EFFECTS_DSL.md). Side benefit: `Op_spendUse` voids on non-Manual events, so Treetreader II (`on=custom`, previously ungated) no longer raises spurious use-card prompts on unrelated triggers.
- [ ] **Treetreader defect 2/3: "move out of a forest" offers only forests (BGA #235064).** CONFIRMED (green test `Campaign_TreetreaderBug235064Test::testMoveOutOfForestButtonOffersOnlyForestBug235064`). SHARED root cause + single fix with defect 3/3: the two effect bullets are in REVERSE order of the two DSL branches. [Op_or::paramInfo](../../modules/php/Operations/Op_or.php#L79) labels `choice_$i` from `effect_(i+1)`, so choice_1 label "Move out of forest" drives branch 1 `move(forest)` (forest-only filter [Op_move.php:66](../../modules/php/Operations/Op_move.php#L66)) -> offers only forest. Expected: adjacent non-forest. Data at [Material.php:4361-4364](../../modules/php/Material.php#L4361) (I) / 4375-4379 (II). FIX (resolves 2/3 AND 3/3 together): align bullet order with branch order (swap the two `<li>` in the `effect` text, or swap DSL to `move(forest)/(in(forest):move)`). CAVEAT (design question for Victoria): even after reorder, the "out" branch `in(forest):move` is an unfiltered move so it still lists forest neighbours too; if intent is "out = non-forest only", the DSL needs a non-forest filter, not just a reorder. Flip assertion once fixed.
- [ ] **Treetreader defect 3/3: "move into a forest" offers forest + non-forest (BGA #235064).** CONFIRMED (green test `Campaign_TreetreaderBug235064Test::testMoveIntoForestButtonOffersNonForestBug235064`). Expected: only adjacent forest. FIX: same bullet/branch reorder as defect 2/3. Flip assertion once fixed.
- [ ] **Multi-kill abilities award XP/gold for only 1 monster (BGA #234247 Sweeping Strike; #234242 Nailed Together = duplicate).** CONFIRMED (green test `Campaign_MultiKillXpBugTest::testSweepMultiKillAwardsXpForOnlyOneMonster`). [Game::countMonsterXp](../../modules/php/Game.php#L591) ignores its `$context` (the monster being finalized) whenever an attack is in progress and instead reads the monster on the shared `marker_attack` hex. In a multi-kill, the cleave's `Op_applyDamage` advances `marker_attack` to the next monster before the first kill's `finishKill`/`finalizeDamage` runs, so the earlier kills read a stale/removed hex and score 0; only the last kill's reward lands. FIX: prefer explicit `$context` when it is a real monster id, fall back to attack-hex only when null (`$monsterId = $context; if null -> hexMap->getCharacterOnHex(getAttackHex())`). Re-run Boldur/Bjorn quest tests (Trollbane `counter(countMonsterXp)` is the only other caller; unchanged on single kills). Flip the test assertion (1 -> 2) once fixed.

- [ ] **Nailed Together II chain re-offers 0-piercing after an exact kill -> softlock (BGA #234580).** CONFIRMED (green test `Op_c_nailedChainSoftlockTest::testChainReoffersZeroOverkillPierceAfterExactKill`). [Op_c_nailed.php:94](../../modules/php/Operations/Op_c_nailed.php#L94) re-queues `c_nailed(chain)` whenever `$willKill` (totalDamage >= health), so an EXACT kill (0 overkill) re-queues a chain step that is void (`getOverkill() <= 0` -> `ERR_NOT_APPLICABLE`) but not skippable: the plain `queue()` passes no `l_skip`, unlike the card-driven op which gets `l_skip=true` from [Card::createOperationForCardEffect](../../modules/php/Model/Card.php#L296). So the void op can't auto-resolve -> "Choose a monster to deal 0 piercing damage to" / "No overkill damage" softlock. FIX: `$this->queue("c_nailed(chain)", null, ["l_skip" => true]);` (also covers the no-monster-behind void case). Flip once fixed.


## Tracked bugs - posponeded
- [ ] **Sweeping Strike "1 cleave hit per attack" cap not enforced in code (follow-up from BGA #233927, pre-existing).** NOT a reported bug yet - flagged during the #233927 fix. The [Op_c_sweep](../../modules/php/Operations/Op_c_sweep.php) docblock claims at most 1 cleave hit per attack, but nothing enforces it; it relies on overkill running out. A cleave that leaves LEFTOVER overkill (e.g. target health 1, overkill 2) with a third live monster on the hero's ring could chain a second cleave. No test yet. Consider enforcing the cap explicitly (dedicated marker/flag) rather than depending on overkill arithmetic.
- [ ] **Heal / removeDamage softlocks when there is no damage to remove (BGA #234859 red crystals).** CONFIRMED (green test `Op_removeDamageSoftlockTest::testGain3RemoveDamageWithNoDamageSoftlocks`). Gaining red crystals queues `NremoveDamage`; when nothing on the board has damage, [Op_removeDamage::getPossibleMoves](../../modules/php/Operations/Op_removeDamage.php) marks every candidate `ERR_NOT_APPLICABLE` -> `noValidTargets()` true, but [Op_removeDamage::canSkip](../../modules/php/Operations/Op_removeDamage.php#L240) returns false, so `canResolveAutomatically()` is false and the top-level dispatch drops into PlayerTurn with no clickable target and no Skip = softlock. (Top-level dispatch never consults `isVoid()`, which is why only the direct-reward path locks; nested-in-seq is fine.) FIX: `Op_removeDamage::canSkip()` should return true when `noValidTargets()` (auto-skip empty). Same base op is shared by heal/repairCard/`all`-mode, so the one fix covers those latent cases. Flip the `canSkip`/`canResolveAutomatically` assertions once fixed.

- [ ] **Optional step-by-step move mode (idea from BGA #234817, Victoria).** Heroes without a step incentive (e.g. Embla) use one-shot `Op_move` (click the final destination, hero paths there and the action ends); players expecting hex-by-hex clicking think movement "ended early" (it did not - they clicked a near hex). #234817 (Embla move) and #235051 (Boldur Wrecking Ball option not noticed) are this discovery-gap family, resolved Not-a-bug / Info-needed. Idea: offer an optional step-by-step move mode (game preference or per-move toggle) so movement can be click-by-click for any hero. Not a bug; design decision, not started. `Op_actionMove::hasStepIncentive` currently gates step mode; a preference would OR into it.
