## Deploy model

Process: **creating a git tag = deployed.** To decide if a fix is live:

- Find the fix commit: `git log --oneline -i --grep='#<reportid>'` (commit messages reference `BGA #<id>`).
- Is it in the latest tag: `git merge-base --is-ancestor <commit> <latest-tag> && echo LIVE`.
- List tags containing it: `git tag --contains <commit> --sort=creatordate | head`.

In the latest deployed tag -> **Fixed**. Committed/tagged but that tag not deployed -> **Waiting for deploy**. When unsure whether a tag is deployed, ask.

It was written up as the "best candidate" for the recurring "Nothing to undo" (#235518, #235653, #235314 remainder); that claim was WRONG and should not be reused. Two corrections: (1) clearing undo history when the turn passes to another player is INTENDED behavior, not damage - and the seat-switch is not even the `0` path, since [OpMachine.php:278](../../modules/php/OpCommon/OpMachine.php#L278) guards `$playerId > 0` and passes a real id, clearing and re-anchoring that one player's rows. (2) The reported symptom was already explained and fixed by 82ca21c (the restore deleted the turn-start barrier, so a second undo failed) - no second mechanism is needed to account for the reports. The residual point below is a code-hygiene nit, NOT a diagnosis, and no report should be attributed to it without a reproducing case. [DbMultiUndo::doSaveUndoSnapshot](../../modules/php/Db/DbMultiUndo.php#L70) runs `clearSnapshotsAfter`/`clearSnapshotsBefore` BEFORE its `player_id == 0 || player_id == 1` early return, and at `player_id == 0` both clears drop their `AND player_id = ...` filter ([DbMultiUndo.php:117](../../modules/php/Db/DbMultiUndo.php#L117)) - so with `barrier=1` the pair deletes `move_id >= X` and `move_id < X` for EVERY player, then returns without saving. The code comment concedes it: "basically with player_id = 0 it will clear all tables". Two callers pass `(int) getActivePlayerId()` unchecked during the monster turn, when there is no active player: [Game.php:479](../../modules/php/Game.php#L479) (`effect_doRollAttackDice`, which also runs for monster attacks) and [Op_rollMonsterDie.php:45](../../modules/php/Operations/Op_rollMonsterDie.php#L45). Why this is NOT a diagnosis: both unguarded callers sit in the monster turn, i.e. between player turns, and the next turn re-anchors a barrier anyway - so even if the cast does hit 0, the clear is harmless in the normal flow. HARDENING (hygiene only): `systemAssert` on `player_id > 1` in `doSaveUndoSnapshot` instead of the silent `return` - a savepoint for player 0/1 should be loud, not a table wipe. Two weaker leads: `customUndoSavepoint` keeps only ONE pending `undoSavepointMeta` per request ([Game.php:857](../../modules/php/Game.php#L857)), so a seat-switch barrier plus a later reveal barrier in one request silently drops one; and [Base::doUndoSavePoint](../../modules/php/Base.php#L664) swallows a failed snapshot write with only an `error()`.
